## 1.2 HTTP requests and responses

Typically, an HTTP client establishes a TCP connection to a particular port on a host (port 80 by
default)
An HTTP server listening on that port waits for the client to send a request message
Upon receiving the request, the server sends back a status line, such as "HTTP/1.1 200 OK",
and a message of its own the body of which is perhaps the requested resource, an error
message or some other information.

## 1.4 Resource identification (URI vs. URL vs. URN)

Resources to be accessed by HTTP are identified using
Uniform Resource Identifiers (URIs) — or, more specifically,
Uniform Resource Locators (URLs) — using the http: or https: URI schemes.

URI/URL use the same format but
• URLs specify a resource that can be fetched
• URIs are only identifiers (e.g., for XML namespaces), i.e., a request to a URI may result in an
error or return an empty document etc.

![[image/Pasted image 20250617125031.png]]


URI: A reference identifying an abstract or physical resource   . Es beschreibt physical addreasse , ist ortsabhaengig 
• Form: `<scheme>://<authority><path>?<query>`
• Can be a URL, URN, or both
- URI 是一个**统称**，用于标识互联网上的资源。它可以用来**定位（URL）** 或 **命名（URN）** 一项资源。

URL: The subset of URIs that identifies resources by their primary access mechanism (e.g.
network location)     Es beschreibt logisch addreasse , ist ortsunabhaengig 

URL 是 URI 的一个子集，用于**定位**资源（即告诉我们如何访问资源，通常包含协议和地址）。
这是我们最常用的类型（浏览器地址栏中的就是 URL）。
• Form = transport://user:password@host:port/path[?search][#fragmentid]
• Is a physical address of a resource
• Example: https://en.wikipedia.org/wiki/Uniform_Resource_Name#URIs,_URNs,_and_URLs

URN: The subset of URIs that uniquely identify a resource independent of its primary storage location
URN 也是 URI 的子集，用于**命名**资源，但不提供访问方式。它的目标是为资源提供一个**持久、唯一的名字**。
这些 URN 表示“某个资源”，但并不能告诉你在哪里能找到它。
• ==Identifier remains stable even is the resource is moved to a different physical location==
• Is a logical address of a resource
• Example: urn:isbn:0451450523

### 1.6.1 Safe und idempotent 

A safe operation is one which changes no state at all. Safe means that the request is intended only for information retrieval and should not change the state of the server
- 意思是：**不会对服务器资源造成改变的操作**。
- 常见的 **safe** 方法有：`GET`、`HEAD`    
- **DELETE 不是 safe 的**，因为它的目的是**删除资源**，显然会改变服务器状态。

An idempotent operation is one which updates state in an absolute way, and ==the result of executing the operation== (注意这里不是 response message 一致与否 ) more than once is the same as executing it once E.g. x = 4 rather than x += 2
- 意思是：**无论你调用一次还是多次，对服务器的结果都是一样的** 。
- `DELETE` 是 **幂等（idempotent）** 的。

假设有一个资源 `/api/item/123`：
- 第一次调用 `DELETE /api/item/123`：成功删除了资源
- 第二次调用 `DELETE /api/item/123`：==资源已不存在，返回 404 或无操作，但**服务器状态不会再次改变**==（还是没有这个资源）


Web-friendly systems scale because of safety
- Caching!

… and idempotent behavior benefits fault tolerance
- Just retry in failure cases


|方法|Safe|Idempotent|说明|
|---|---|---|---|
|GET|✅|✅|只读|
|POST|❌|❌|每次调用可能都创建新资源|
|PUT|❌|✅|多次更新结果一致|
|DELETE|❌|✅|多次删除效果一样|

### 1.6.5 DELETE : Delete 

Stop the resource from being accessible
 Logical delete, not necessarily physical (data are often tombstoned): This is important for decoupling implementation details from resources   . 不是真正的删除 

Request
```

Host: example.org
```



Response
```

200 OK
Content-Type: application/xml

        halvards
</admin:userDeleted>
```



When DELETE goes wrong
DELETE again!
• Delete is idempotent
• DELETE once, DELETE 10 times has the same effect: (at most) one deletion

Some 4xx responses indicate that deletion is not possible
• The state of the resource is not compatible
• Try forward/backward compensation instead

**Recursive DNS Server**
**递归 DNS 服务器**是指帮你“从头到尾查域名”的 DNS 服务器。

当你在浏览器中输入一个网址（如 `www.google.com`）时，这个服务器会**负责从根开始，一步一步找出最终的 IP 地址**。

> 你可以把它理解成一个**“中间人”**，专门负责**替你向其他服务器打听**这个网址的 IP 地址。


- 用户访问 `www.google.com`，请求发到递归 DNS 服务器。
    
- 它问根服务器：“.com 的服务器是谁？”
    
- 然后问 `.com` 的服务器：“google.com 的服务器是谁？”
    
- 最后问 `google.com` 的服务器：“[www.google.com](http://www.google.com) 的 IP 是啥？”
    
- 得到 IP 后，它把结果返回给浏览器。


----

**Authoritative Name Server**（权威 DNS 服务器）？

**权威 DNS 服务器**是指**真正知道某个域名 IP 的服务器**，是**“最终答案的来源”**。

当递归服务器一路打听下来，最终会找到一个**权威服务器**来获取真正的 IP。

> 举例来说，如果你拥有域名 `example.com`，那么你可以设定自己的权威 DNS 服务器，它记录了你网站的 IP 地址。


对于 `www.google.com`，最终的权威服务器是由 Google 管理的，它知道这个域名对应的 IP 是什么。


---

什么是 Root Name Server（根服务器）？
✅ 定义：

根 DNS 服务器是整个 DNS 系统的最顶层，负责告诉你每个顶级域（如 .com、.org、.cn）由谁管理。

    它不会告诉你域名的最终 IP，但它会说：“你可以去问 .com 的服务器。”
- 有 13 个逻辑根服务器，分别用字母命名（如 A-root, B-root...）
    
- 这些服务器是全球 DNS 系统的核心起点，**递归 DNS 服务器查询域名时的第一站**就是根服务器。

# 3 Web APIs

Web APIs
- Programmierschnittstellen auf Basis von HTTP (REST oder SOAP)
- Datenformate meist JSON oder XML
- Ermöglichen systemübergreifende Kommunikation (z. B. Wetter, Maps, Login)
- Moderne APIs sind in der Regel REST-basiert, ältere Systeme nutzen häufig noch SOAP/WSDL


An Application Programming Interface (API) is a way for multiple computer programs to communicate. If they communicate via the Web, it’s a Web API.
Modern (web) applications often use multiple web APIs, e.g., when embedding APIs for ads, maps, payment, social media, etc.
Web APIs are based on open standards – in the past, mostly based on SOAP/WSDL; today, mostly using REST.
But: There are no strict rules that describe how the interface of a Web API should look

Web APIs in a nutshell: A server exposes endpoints (usually HTTP(S)) with request-response interaction, often using JSON or XML as payload. The endpoints are called by clients, e.g., from a web browser (=> AJAX), mobile app, or a backend server.


SOAP/WSDL web services:
• First attempt at enabling web-based integration of remote services
• Still common in enterprise contexts (but not called from mobile or web apps)
• Can use arbitrary transport protocols
• Extensibility of enterprise-grade features (security, reliable messaging, routing, …)

- **首次尝试通过 Web 实现远程服务集成**：  
    SOAP（Simple Object Access Protocol）和 WSDL（Web Services Description Language）是早期用于系统之间远程通信的标准方式，最初用于解决跨平台系统之间如何远程调用函数的问题。
    
- **今天仍在企业环境中广泛使用**：  
    尽管它比较重，SOAP/WSDL 在大型企业的后端系统（如银行、保险、政府）中依然常见，但它们通常不会被移动或 Web 应用直接调用。
    
- **可使用任意传输协议（不止 HTTP）**：  
    与 REST 只能基于 HTTP 不同，SOAP 可以运行在多种协议上，比如 SMTP、JMS 等，具备更高的灵活性。
    
- **可扩展性强，支持企业级特性**：  
    比如安全性（WS-Security）、可靠消息传递（WS-ReliableMessaging）、路由控制等，SOAP 的一大特点就是支持这些复杂功能




RESTful services:
• Developed as lightweight alternative to SOAP/WSDL
• De facto standard today
• In essence: programmatically using HTTP-only, the way HTTP was intended to be used

- **作为 SOAP 的轻量替代方案出现**：  
    REST（Representational State Transfer）诞生于对 SOAP 的简化，它强调简单、无状态、资源导向，使用 HTTP 的标准方法（GET, POST, PUT, DELETE 等）。
    
- **已成为事实上的主流标准**：  
    目前，大多数现代 Web 和移动应用都使用 RESTful API 与后端进行通信。
    
- **本质上：使用 HTTP 的本来设计方式进行编程**：  
    REST 不是协议，而是一种架构风格，它将每个 URL 当作资源，并通过标准 HTTP 方法对资源进行操作，是最贴近 HTTP 初衷的用法。



GraphQL:
• Technology for getting data from RESTful APIs in a declarative way
**用于从 REST 接口中以声明式方式获取数据的技术**：  
GraphQL 由 Facebook 开发，它允许客户端根据自身需求**声明式**地请求数据（比如只要 name 和 email），而不是像 REST 那样依赖服务器提供固定的响应结构。


|比较维度|SOAP/WSDL - XML|REST - JSON|
|---|---|---|
|格式/风格|重/正式/结构严格|轻量/灵活/结构简单|
|扩展性|高（支持各种复杂功能）|低（但也因此简单）|
|易用性|学习和实现成本高|更易开发，社区支持广泛|
|使用场景|企业级、规范严格的后端系统|Web、移动端通信，现代微服务架构等|



- 企业后端遗留系统 ➜ **SOAP/WSDL**
- 日常 Web / App 开发 ➜ **REST*    
- 需要前端定制查询效率（如 GraphQL Playground）➜ **GraphQL**







## 3.1 SOAP/WSDL web services and the WS-* platform

SOAP was originally created in 1999 (as “XML-RPC”). Since 2001 the W3C has been working on SOAP (“Simple Object Access Protocol”). Since 2003 SOAP no longer is an acronym. ## 3.2 SOAP 


SOAP provides a basic mechanism for:
- encapsulating messages into an XML document
- mapping the XML document / SOAP message to an HTTP request
- transforming RPC calls into SOAP messages
- processing a SOAP message

SOAP takes advantage of the standardization of XML to resolve problems of data representation and serialization (it uses XML Schema to represent data and data structures, and it also relies on XML for serializing the data for transmission)



what is SOAP? 
1. A message format for one-way communication describing how a message can be packed into an XML document 
2. A description of how the message (the XML document) should be transported using HTTP (for Web based interaction), SMTP (for e-mail based interaction), or other transport protocols 
3. A set of rules that must be followed when processing a SOAP message and a simple classification of the entities involved in processing a SOAP message. It also specifies what parts of the messages should be read by whom and how to react in case the content is not understood. 
4. A set of conventions on how to turn an RPC call into a SOAP message and back, as well as how to implement the RPC style of interaction

## 3.3 WSDL



WSDL Summary

WSDL includes a grammar and syntax on top of XML Schema to describe Web services as a set of communication endpoints. A complete WSDL definition contains all necessary information to invoke a web service.

The data being exchanged between the endpoints is specified as part of messages and every kind of processing activity allowed at an endpoint is considered as an operation.

The WS-* set of standards supports many different extensions to the “simple” use case: for example, success answers and error messages could be sent to different receivers.

----


XML-based
Platform- and language-independent
Describes a “contract“ between service provider and requester

Contains information on
• What a service does (the operations)
• Where a service resides (an address)
• How to invoke a service (data formats, protocols)

Generally, also usable with other message formats – in practice, used as SOAP’s IDL to form
SOAP/WSDL.

### 3.3.1 WSDL Documents

Every WSDL Document contains two sections:

Abstract description
• types: describes messages and their payloads (based on XSD)
• operation: groups opt. input and output messages (~ Java method)
• interface: combines one or more operations that constitute an abstract service (~ Java interface)

Concrete/Implementation description
• binding: maps an interface to a transport protocol
• endpoint: network address of the binding
• service: collection of endpoints


#### 3.3.1.1 Abstract part 

WSDL Documents: `<types>`

The WSDL `<types>` element contains all abstract data types that define a web service interface
The `<types>` element in WSDL uses XML schema to define simple and complex types which are
used as parameters and return values for operations. The elements defined are referenced later
in the WSDL document.

Comparison to gRPC:
The types element is equivalent to the proto file content without the service {} entry.


----

WSDL Documents: `<interface>, <operation>`

```
A <interface> element defines an abstract type and its operations, but not an implementation.
An <interface> element is a logical grouping of <operation> elements.
• It describes the kinds of operations that a web service supports – the messaging mode
and payloads – without specifying the Internet protocol or physical address used
• The <interface> element is central to a WSDL description; the rest of the elements in the
definition are essentially details that the <interface> element depends upon

Operations in WSDL represent the functions exposed by the service: they include the name of
the function and the input and output parameters. An <operation> element is composed of
<input> and <output> elements (at most one each) and any number of <fault> elements.

Comparison to gRPC:
<interface> is equivalent to the service {} entry in the proto file.
<operation> is equivalent to the rpc line in the service {} entry.
```

## 3.4 SOAP WSDL 区别 

SOAP 和 WSDL 是 Web 服务技术中的两个关键概念，它们关系密切但用途不同：

SOAP（Simple Object Access Protocol）
是一种 **通信协议**，用于在网络上交换结构化信息。
- 是一种基于 XML 的协议。
- 用于在客户端和服务器之间发送消息。
- 通常使用 HTTP 或 SMTP 作为传输协议。
- 定义了消息的格式、数据的封装方式，以及调用远程方法的规则。
📌 **作用：**  
描述服务的接口（像说明书一样）——方便工具生成代码，或手动编写请求。





WSDL（Web Services Description Language）

是一种 **接口描述语言**，描述了一个 Web 服务的 **可调用方法、参数、数据类型、返回值** 等。
- 是基于 XML 的语言。
- 告诉客户端：服务端提供了哪些方法、如何调用、在哪儿调用。
- 通常与 SOAP 配合使用，自动生成客户端代码。
📌 **作用：**  
传输数据（请求和响应）——比如客户端调用服务器上的某个方法。

| 项目   | SOAP                      | WSDL               |
| ---- | ------------------------- | ------------------ |
| 类型   | 通信协议                      | 接口描述语言             |
| 格式   | 基于 XML                    | 基于 XML             |
| 用途   | 发送请求和响应                   | 描述 Web 服务接口        |
| 作用对象 | 传输数据（运行时使用）               | 描述服务结构（开发时使用）      |
| 通常关系 | 依赖 WSDL 定义的方法结构发送 SOAP 消息 | 描述了可以通过 SOAP 调用的服务 |

如果你把 Web 服务比作“电话系统”：
- **SOAP** 是电话线路上说的话（消息），    
- **WSDL** 是电话号码簿 + 使用说明（有哪些号码，打给谁，说什么）。


## 3.5 REST


The concepts of REST were developed by Roy Fielding in 2000 and are generally used as the standard for web APIs today.

General Idea: The web is a scalable and reliable system -> formalize this style and use it for future system. Use HTTP, the basis of the web, also for programmatic API interaction.


New concept:
• Everything is an (abstract) resource which we can modify (=> CRUD)
• The implementation decides how the change of the resource is reflected in server data.

### 3.5.1 REST constraints

Roy Fielding defined six constraints for the REST architectural style. 
A system that fulfils these requirements gains non-functional properties such as performance, scalability, simplicity, modifiability, portability, and reliability:
- Client-server Architecture
- Statelessness
- Cacheability
- Layered System
- Uniform Interface
- Code on demand

In practice, some of them are relevant to REST, others only for the part of the web directly interacting with humans.


---

1  Client-server architecture

- Trennung von Benutzeroberfläche und Datenverwaltung, sodass beide unabhängig voneinander weiterentwickelt werden können.

Separation of Concerns: Separate the user interface from the data storage. This allows the server and clients to evolve separately.
To implement this, we use web browsers to present information to users, and use web APIs to deliver data from servers to clients.


---

2 Statelessness
不能用 session 但是能用  cookies 去满足 stateless 的这个条件 

- Jede Anfrage ist eigenständig und enthält alle nötigen Informationen. Der Server speichert keinen Sitzungszustand.
- Falls Zustand benötigt wird, kann dieser durch Cookies vom Client mit jeder Anfrage mitgeschickt werden.

Use a communication protocol in which the receiver does not need to retain session information from previous messages.

I.e., every new message can be processed by a different application server. If the client needs state, the request must contain all information necessary to respond to the request.

We can implement this using HTTP Cookies, which are sent with every request.

⇒ The interaction itself does not hold state (there is no concept of a session)
⇒ State is only held by the client (and to some degree by the server in the form of resources)


---
3 

Cacheability 

- Antworten müssen als cachebar oder nicht-cachebar gekennzeichnet sein, um die Leistung zu verbessern.
- Web-Caches können so Anfragen effizienter beantworten. HTTP GET-Anfragen sind oft cachebar.

A Web cache stores HTTP responses so that future requests can be served the cached response instead of forwarding the request to an application server. It can sit on every component between the client and server (and even on the client!). In REST, every response must define itself as cacheable or non-cacheable. This can eliminate requests, which increases scalability and performance. In the Web, HTTP GET requests are often considered cacheable, and all other methods are not.


---

4 Layered System 
The client can not tell whether it is talking to the application server or is connected to an intermediary server. This node could be a cache, proxy, load balancer, … Intermediary servers could also send request to multiple other servers before delivering an answer. Making this transparent* to the client allows us to improve scalability without changing anything in the client

- Der Client weiß nicht, ob er direkt mit dem Server oder über Zwischeninstanzen (z. B. Proxy, Load Balancer) kommuniziert.
- Zwischenserver können vor der Antwort weitere Server anfragen.



---

5 Uniform Interface

- Ressourcen haben eindeutige URIs.
- Ressourcen werden in neutralen Formaten (z.B. JSON, XML) dargestellt.
- Nachrichten enthalten alle nötigen Informationen, um sie zu verarbeiten.
- HATEOAS: Clients erhalten Hyperlinks, um weitere Aktionen auf Ressourcen zu entdecken.

The interface between servers and clients should always follow a familiar pattern:

1 
Resource Identification: Every resource can be identified, e.g., by a URI
Everything that might need to be identified can be a resource, e.g.: 
• Products in an online shop 
• Categories used for grouping products 
• Customers and their shopping carts 
-> Similar to object-orientation

2 
Resource Manipulation through Representations: The current or intended state of a resource is shown in a neutral format, so that the client does not need to know the internals of the server. 

I.e., a web service might store its data in a SQL database (or even generate them on the fly), but will always deliver XML/JSON to the clients.

The server-side implementation can be replaced at any time without affecting the interface

通过表现形式进行资源操作：资源的当前状态或期望状态以一种中立的格式展示，使客户端无需了解服务器的内部实现。

也就是说，一个 Web 服务可能将数据存储在 SQL 数据库中（甚至是实时生成的），但始终以 XML 或 JSON 的形式向客户端提供数据。

服务器端的实现可以在任何时候更换，而不会影响对外提供的接口。



3 
Self-descriptive Messages: Every Message should include all necessary information to process it. E.g., the media type (JSON, XML, …) needs to be specified.

Use the HTTP “Accept” and “Content-Type” Headers

自描述消息：每条消息都应包含处理该消息所需的所有必要信息。例如，需要指定媒体类型（如 JSON、XML 等）。

➡ 应使用 HTTP 的 “Accept” 和 “Content-Type” 头部字段。


4 Hypermedia as the engine of application state (HATEOAS): A REST client should be able to discover all resources it needs after accessing an initial URI. 

Human analogy: A user can navigate the whole website after visiting the landing page. 

Server needs to send hyperlinks to other resources with every response (e.g., “you can also get the reviews, the price, the product details, or related products for the product you just requested”).

4 超媒体作为应用状态的引擎（HATEOAS）：一个 REST 客户端在访问初始 URI 之后，应该能够发现它所需要的所有资源。

类比于人类的行为：用户访问网站的首页后，就可以浏览整个网站的所有内容。

➡ 因此，服务器需要在每个响应中附带指向其他资源的超链接（例如：“你还可以获取该产品的评论、价格、产品详情或相关产品信息”）。


---


6 Code On Demand 

- Der Server kann Code (z.B. JavaScript) an den Client senden, um dessen Funktionalität zu erweitern.

Servers can change the functionality of a client by executing code inside the client 

executing JavaScript inside the browser (=not directly related to REST

# 4 GraphQL

Sending complex queries to Web APIs is a common use case – with GraphQL, we can declaratively express our queries. 

GraphQL is a query language and a server-side runtime for executing those queries. It uses a type system to define the data, and can use multiple different database backends. 

This way, clients can send a single request with a complex query to a server, and the server will perform all necessary steps to get the result of this query. This might include sending requests to multiple other web APIs.

**GraphQL** 是一种用于 **API 查询语言（Query Language）** 和 **服务器端运行时（Runtime）** 的技术，由 Facebook 在 2012 年开发，并在 2015 年开源。它是 REST 的一种替代方案，旨在更灵活、高效地获取客户端所需的数据。

GraphQL 允许客户端明确地请求它想要的数据，避免过多（over-fetching）或过少（under-fetching）的问题。
> **GraphQL lets clients request exactly the data they need — nothing more, nothing less.**



|特点|解释|
|---|---|
|**灵活的数据查询**|客户端可以精确指定需要哪些字段，而不是依赖固定的服务器端响应结构。|
|**单一端点**|所有请求通常通过一个 `/graphql` 端点发送，而不是像 REST 那样为每个资源定义不同的路径。|
|**组合查询**|可以在一个请求中同时获取多个相关资源的数据（如用户信息 + 订单列表），减少 HTTP 请求次数。|
|**强类型系统**|GraphQL 使用一种叫做 **Schema（模式）** 的定义语言来约定数据结构和类型。|
|**实时支持（可选）**|通过 **GraphQL Subscriptions** 可以实现 WebSocket 方式的实时数据推送。|

|Feature|Description|
|---|---|
|**Flexible data queries**|The client can specify exactly which fields to retrieve.|
|**Single endpoint**|All requests are sent to a single endpoint (e.g., `/graphql`) instead of multiple REST URLs.|
|**Data aggregation**|Fetch multiple related resources in a single request (e.g., user + posts + comments).|
|**Strongly typed schema**|GraphQL APIs are defined by a strict type system (schema).|
|**Real-time support**|GraphQL can support real-time data with **subscriptions** (usually over WebSockets).|




|方面|GraphQL|REST|
|---|---|---|
|数据请求|客户端决定需要哪些字段|服务器定义返回内容|
|端点数量|通常一个 `/graphql`|每个资源一个 URL|
|请求效率|高，避免冗余/不足|可能 over-fetch 或 under-fetch|
|学习曲线|相对较陡，需要 Schema 和查询语法|比较简单，基于 HTTP 方法|

| Feature        | GraphQL                                             | REST                                  |
| -------------- | --------------------------------------------------- | ------------------------------------- |
| Data fetching  | Client specifies exact fields                       | Server defines what to return         |
| Endpoints      | One endpoint (`/graphql`)                           | Multiple endpoints (one per resource) |
| Over-fetching  | Avoided                                             | Common                                |
| Under-fetching | Avoided                                             | Common                                |
| Learning curve | Steeper (requires learning schema & query language) | Simpler (standard HTTP verbs)         |

```graphql
{
  product(id: "123") {
    name
    price
    reviews {
      rating
      comment
    }
  }
}
```
