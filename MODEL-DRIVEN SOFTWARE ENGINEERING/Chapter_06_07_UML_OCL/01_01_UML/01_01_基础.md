• Aktuelle Version (seit Juni 2015): UML 2.5
• Spezifikation: http://www.omg.org/spec/UML/

Associations are therefore the basis for constructing your own complex data types. The navigability of the association has so far been unspecified in the model. In the code, it has simply been assumed that navigability should be possible in both directions, i.e., that a bidirectional association exists.

### 6.1.3 types of associations

Basically, the following types of associations can be distinguished with regard to their cardinality:
- **1:1 relationship** : Each object of type K1 is assigned a maximum of one object of type K2 , and vice versa. Example: "Man is married to woman."
- **1:N relationship** : Each object of type K 1 can be assigned any number of objects of type K 2 , but for each object of type K 2 there is a maximum of one object of type K 1 . Example: "Mother has children."
- **N:N relationship** : Any number of objects of type K 2 are assigned to each object of type K 1 and vice versa. Example: "Order includes product."

A reflexive association occurs when multiple objects of the same class are related to each other.

## 6.2 Aggregation and composition

If an association end needs to be highlighted to indicate that it is a part-whole relationship, UML offers aggregation and composition as special associations. An open diamond on the aggregate side indicates an aggregation, while a filled diamond represents a composition. The objects involved in a part-whole relationship always form an acyclic graph.

- **Aggregation** : The semantics of a weak part-whole relationship consist solely in the fact that the aggregate can, logically, assume certain tasks as a representative for its parts, e.g., a department for all its employees. Fundamentally, the distinction between association and aggregation is difficult.  不是强跟随 不会跟着一起删除 
- **Composition** : The strong part-whole relationship is composition. In composition, a part can only belong to one aggregate at a given time. The part is copied or deleted together with the aggregate. Its existence depends on the aggregate. 跟着一起删除   This seems obvious for the example shown here of files as parts of a directory in the file system. If we delete a directory in the file system, for example, we also remove all the files in that directory. Even if we copy the directory to another location, we equally duplicate all the files in the directory. A file can only be in one directory at a time.

## 6.3 Inheritance and polymorphism



### 6.3.1 Inheritance: subclass and superclass 
Classes can extend other classes. Specialized subclasses can inherit attributes and methods from more general superclasses. Inheritance is the basic concept of class reuse. An inheriting/derived class possesses all the attributes and methods of the class from which it inherits/derives. Additional specialized attributes and methods can be added to the new class, but it always remains compatible with the superclass, i.e., it conforms to its interface. An object of the subclass can be used wherever an object of the superclass is expected, e.g., as an input argument to a method.


In UML, inheritance is represented by block arrows pointing from the subclass to the superclass. In the following example, there are two special types of Person, namely `Employee`and `Freelancer`. These two subclasses share the general attributes of the superclass `Person`and each add specific attributes. Similarly, methods (and constructors) can be inherited from the superclass, and new methods (and constructors) can be added in the subclass.






```java
abstract class Person {
	Integer id;
	String name;
}



class Employee extends Person {
	Integer salary;
	Integer overtime;
}

class Freelancer extends Person {
	Integer dailyRate;
}
```

An interface usually only specifies method signatures, which then form a common interface for all classes that implement the interface. An interface therefore corresponds to an abstract class with only abstract methods. Since Java 8, however, default implementations for methods can also be specified in interfaces. Since an interface has no attributes and no associations, it is stateless. The following example shows the two classes Rectangleand Circle, which each implement the interface Shapeand must therefore override its methods. If the methods of the interface are generally known and a class implements a large number of interfaces, the so-called Lollipop notation is a useful shorthand notation to maintain clarity in a larger model.

Lolipop-Notation 代表 interface class 

![[image/Pasted image 20250409133413.png]]

```java
interface Shape {
    Double perimeter();
    Double area();
}

class Circle implements Shape {
    Double radius;

    @Override
    Double perimeter() { return 2 * Math.PI * radius; }
    @Override
    Double area() { return Math.PI * radius * radius; }
}

class Rectangle implements Shape {
    Double width, height;

    @Override
    Double perimeter() { return 2 * (width + height); }
    @Override
    Double area() { return width * height; }
}

interface Shape {
    default Double perimeter() { return null; }
    default Double area() { return null; }
}

```

## 6.4 Association classes and multi-place relationships


A special type of class is an association class, which adds attributes to an association. An object of the association class cannot exist without a corresponding object at both ends of the association. In the following example, a person works a certain number of hours ( `hoursWorked`) performing a specific activity ( `activity`) on a project. In total, many people can work on many projects.


![[image/Pasted image 20250409133559.png]]

The same relationship can alternatively be modeled without an association class as follows.
![[image/Pasted image 20250409133635.png]]

Modeling an N:N relationship with attributes without an association class

An association class can, in turn, be related to other classes. In the following example, the information about the location ( `Location`) from which a person works on a project is added. This creates a ternary relationship between the classes `Person`, `Project`and `Location`. In the set representation outlined below, person X works from location 1 on project A , person Y from location 2 on project B , and person Y from location 1 on project C . Any number of other combinations are also possible. In principle, multi-place relationships can be modeled in different ways in the UML (even without using an association class).
